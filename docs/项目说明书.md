## 一、摘要

团队协作分工智能体是一套让全模态大模型直接参与团队协作的 Web 应用。以往的项目管理工具要求先把语音、照片、会议录像整理成文字，再手工拆成任务；这套系统把 MiniCPM-o 4.5 的听、说、看能力直接接进计划流程，拍照立项、说话排期、会议录像边看边听，成员用一条语音或一张照片就能汇报进度，计划随现实变化自动重算，从需求到执行再到反馈形成完整闭环。

评审可直接体验公网 Demo：[collaboration-planner-demo-l6ag.onrender.com](https://collaboration-planner-demo-l6ag.onrender.com)（账号 admin，密码 ascend2026）。线上实例运行云端 MiniCPM-o 后端；演示视频按功能双轨录制，全模态交互（拍照、语音、会议旁听、语音汇报）走云端，计划引擎（任务拆解、分工、排期）走本地昇腾 A3，两套后端共用同一套代码与接口。

以上两段描述的是已经建成并实际运行的系统，系统能否落地可以用三组依据直接查证：全量 401 项自动化测试无需配置任何模型密钥即可离线复现，覆盖计划引擎、多模态接口、汇报闭环与导出；昇腾 A3 环境完成了真实部署与实测，文本对话约 2 秒、语音理解约 8 秒、图片理解约 7 秒返回；公网实例持续在线，云端全链路实测会议录像边看边听端到端约 16 秒。

## 二、项目是什么、定位与价值

### 2.1 项目是什么

团队协作分工智能体是一套把项目要求转化为可执行协作方案的 Web 应用。用户输入项目背景、截止日期、团队成员和成员技能，系统自动完成任务拆解、技能匹配分工、关键路径排期和项目报告生成；方案生成之后，成员可以随时修改任务、调整分工、更新状态，系统即时重算排期与负载；负责人通过成员汇报链接掌握进度，状态变更自动推送到群。

系统的完整流程可以概括为五个环节：拍照立项，说话排期，确认分工，语音或照片汇报，群通知触达。这五个环节依次对应项目启动、计划生成、人工确认、执行反馈和结果触达，共同构成一个从需求到执行的闭环。

### 2.2 项目定位

本项目面向华为昇腾创新应用赛道，定位是把多模态大模型从对话工具变成协作流程的组成部分。赛事围绕 MiniCPM-o 4.5 全模态模型在昇腾 NPU 上的推理与应用落地展开。本项目的技术路线可以用一句话概括：模型负责创造性的内容理解与生成，确定性算法负责计划数据的正确性，两者各司其职，协同完成协作闭环。

### 2.3 解决什么问题

团队协作的计划管理存在四类长期问题：静态计划表快速过时，项目变化后要人工维护，负责人花费大量时间追问进度并手工重排；多模态信息需要人工二次整理，课程说明、白板讨论、会议录音和群聊截图要先转写、提炼才能变成任务，费时且容易遗漏；成员更新状态的成本高，日常汇报依赖开会和群聊，负责人难以掌握真实进度；会议中形成的分工和安排散落在聊天记录里，事后难以追溯。

这四类问题的共同根源，是输入通道与反馈通道都和计划脱节：语音、图片、视频材料进不了计划系统，任务状态又难以及时回流。本项目把两条通道同时打通，输入端用全模态模型理解原始材料并直接参与拆解，输出端用轻量汇报页和群通知让状态变化自动回流。

### 2.4 为什么有价值

这套系统的价值可以从三个角度来理解。对使用者而言，它把"读要求、拆任务、排工期、盯进度"这类重复劳动交给算法和模型，人只需要做判断和确认；对组织者而言，汇报链接、群通知和版本回滚让进度透明、变更可追溯；对行业而言，项目验证了全模态模型可以作为业务流程的输入通道，与确定性算法协同工作。

### 2.5 与现有方案的差异

| 方案类型 | 代表性形态 | 主要局限 |
| --- | --- | --- |
| 通用任务管理工具 | Trello、飞书任务、Notion | 任务需手工创建，拆解、排期、技能匹配靠人完成；语音、照片等材料需人工整理 |
| 通用甘特图软件 | MS Project、在线排期工具 | 排期固定，成员变动与状态变化后需手工重排；缺少技能匹配和负载均衡 |
| 通用对话式大模型 | 各类聊天助手 | 能对话和生成建议，但没有方案状态、没有计划数据、没有确定性算法保证 |
| 本项目 | 协作分工智能体 | 全模态材料直接进拆解；排期、分工、负载由确定性算法保证；汇报、通知、版本形成闭环 |

需要说明的是，以上工具各有其适用场景。本项目的目标是在项目计划生成与持续维护这一环节上补齐自动化能力，并把多模态交互接入其中，与现有工具形成互补。

## 三、系统设计与技术实现

本章说明系统的架构、核心机制与实现边界，回答"系统内部如何工作"。

### 3.1 总体架构

系统采用前后端分离的 Web 架构。前端是原生 JavaScript 单页应用，提供项目工作台和成员轻量汇报页两个入口，浏览器直接加载，没有构建步骤；后端是 FastAPI 服务，按业务域拆分为计划、实时对话、媒体分析、成员汇报、导出和系统等路由；推理层由昇腾 A3（910C）上的 llama.cpp-omni 与 ModelBest 云端 Realtime API 组成，通过环境变量切换，上层接口完全一致。

```text
浏览器前端（工作台 + 成员轻量汇报页）
  文本 / 语音 / 拍照 / 录像 / 甘特图 / 导出
        │  HTTP / WebSocket
        ▼
FastAPI 后端（/api）
  计划引擎：拆解 → 分工 → CPM 排期 → 报告
  多模态适配：本地直听 / 云端先转写再理解
  媒体分析：抽帧 / 图片理解 / 扫描 PDF / 音频转写
  协作闭环：汇报令牌 / 负责人确认 / 群通知
        │  WebSocket /backend
        ▼
昇腾 A3（910C） - llama.cpp-omni / MiniCPM-o-4_5-F16（计划引擎·本地）
        │  WebSocket 云端 API
        ▼
ModelBest 云端 - MiniCPM-o-4.5-Realtime（全模态·线上）
```

部署采用双轨形态，两条轨道通过环境变量切换。

### 3.2 多智能体架构

这套系统由多个子智能体协作组成，系统能力来自组件之间的分工配合，单个模型的调用只是其中一部分。每个子智能体负责一类工作，通过约定的数据结构把结果交给下一个组件；每个环节的输入输出清晰、可以被单独校验，任何一个环节出问题都有明确的定位和兜底路径。

#### 3.2.1 子智能体组成与职责

| 子智能体 | 职责 | 主要输入 | 主要输出 | 实现方式 |
| --- | --- | --- | --- | --- |
| 任务拆解（Planner） | 把项目要求拆成弹性子任务 | 项目背景、成员、截止日期、文件分析结果 | 1 至 8 个子任务（名称、说明、工时、依赖、技能、建议人数） | 模型生成，失败切换确定性蓝图 |
| 分工（Matcher） | 按技能与负载分配人员 | 任务计划、成员档案 | 负责人、主要协助、辅助协助、匹配评分、负载摘要 | 模型初稿加确定性评分校正 |
| 排期（Timeline） | 计算关键路径与起止日期 | 任务计划、分工结果、成员可用性 | 每个任务的起止日期、浮动天数、关键路径标识 | 纯算法（CPM） |
| 报告（Reporter） | 汇总计划与风险成文 | 任务、分工、排期 | 项目报告 | 模型生成，模板兜底 |
| 批判性审查（Reflection） | 检查计划风险并给建议 | 任务、分工、排期 | 风险清单、改进建议 | 确定性风险门加模型建议 |
| 答辩模拟（InterviewSim） | 依据材料生成答辩问题并多轮追问 | 答辩材料、方案 | 模拟问题与追问 | 模型生成，规则兜底 |
| 知识问答（KnowledgeAgent） | 检索跨项目经验并合成回答 | 问题、当前方案 | 回答与工具调用轨迹 | 工具调用加模型合成 |

#### 3.2.2 协作机制与数据契约

子智能体之间不直接互相调用，协作通过统一的数据契约完成：每个子智能体的输入和输出遵循预先定义的结构，拆解产出任务计划，分工产出分配矩阵，排期产出时间线，报告汇总三者成文。每个子智能体读取前序输出、写入自身输出，输出经过结构校验后才进入下一环节，格式错误在源头被拦截。

调度器负责编排这条主链路：拆解完成后传入分工，分工完成后传入排期，排期与分工共同传入报告，报告完成后进入批判性审查。每个阶段都有独立的超时、重试和兜底路径，单个子智能体失败不会中断整条链路。批判性审查给出的改进建议回到用户界面，由人决定是否采纳；知识问答子智能体具备工具调用能力，可以检索负载、日历、提醒与复盘结果后合成回答，工具调用轨迹随回答展示；答辩模拟只依据实际答辩材料生成问题，与方案无关的材料不参与提问。各组件可脱离 Web 服务独立运行验证，命令行工具提供 planner、matcher、timeline、reporter、interview、full 等子命令，输入输出均为可读 JSON；排期等纯算法子智能体不依赖网络与模型。

#### 3.2.3 任务拆解

任务拆解是主链路的起点。拆解组件接收项目背景、成员信息和截止日期，生成 1 至 8 个弹性子任务，每个任务包含名称、说明、工时、依赖、所需技能和建议人数。模型输出要经过结构校验：任务编号去重、悬空依赖剔除、依赖环检测，新生成的任务统一从"待开始"状态起步，防止模型把任务直接标记为已完成。模型失败或输出不合法时，系统依据文件分析和领域模板生成确定性任务蓝图，拆解环节不会成为整条链路的断点。

#### 3.2.4 分工与负载均衡

分工由模型给出初步分配，再由确定性评分模块校正。评分模块实现中文、近义词和中英文技能匹配，支持负向技能标签，也就是成员明确表示回避的技能在分配时会被排除；分配结构采用负责人、主要协助、辅助协助三层角色，单人或小组任务按建议人数决定协作规模。

分工质量由四个维度加权计算：技能匹配占 0.55，成员总负载占 0.20，阶段负载占 0.15，剩余可用产能占 0.10。技能匹配决定任务能否按期完成，权重过半；总负载、阶段负载与剩余产能合计 0.45，防止技能最优的结果把任务堆给少数成员。总负载反映长期负担，阶段负载反映同一时段的任务重叠，更贴近短期瓶颈，因此分开计权；不可用日期与每日工时已在排期阶段硬性处理，剩余产能只保留边际影响。

协作工作量按角色折算：负责人记全额工时，主要协助记三成，辅助协助记一成半，防止"协助"虚增负担。负载均衡以最重与最轻成员的工作量差不超过 1 小时为目标，这个阈值对应排期半天粒度的四分之一，再小会频繁推翻技能更优的分配，再大则失衡可见；重分配保留用户手动固定的人员分配和已有状态，成员不可用日期在分配中硬性跳过。

#### 3.2.5 关键路径排期

排期使用 CPM 关键路径法（Critical Path Method），以半天为最小粒度。算法先对任务做拓扑排序，再执行前向与后向遍历，计算出每个任务的最早与最晚时间、关键路径标识和浮动天数。排期从截止日期倒推，跳过周末和成员不可用日期，按成员每日可用工时折算任务窗口；如果倒推结果早于今天，就从今天正排并提示延期。

任务窗口按可用工作日累计，周末与不可用日期作为空档跳过，多日任务会自动拉长以覆盖空档，资源日历在这些日期不产生负载。浮动天数表示任务可延迟的裕量，关键路径上的任务浮动为零；甘特图用颜色区分关键路径、缓冲较少、缓冲充裕和阻塞四种状态，排期明细直接显示每项任务的起止日期和浮动天数。排期结果与甘特图、资源日历共用同一份数据，任何一处修改都能在全部视图同步。

#### 3.2.6 报告与批判性审查

报告组件汇总任务、分工、时间线和风险，生成可导出的项目报告。批判性审查先由确定性风险门判断是否值得调用模型：未分配任务、技能匹配低于阈值、负载失衡、产能超载、关键路径过长、依赖环和截止日期风险都会触发审查；触发后由模型针对命中的风险给出可执行的改进建议。风险门保证审查有依据，模型只负责补充建议。

#### 3.2.7 工时估算知识库

工时估算由独立的知识库服务支撑。系统维护结构化工时案例库，按任务语义检索相似案例给出参考工时；用户修正后的实际工时自动沉淀回知识库，形成反馈闭环。这意味着同类任务的估算会随着使用逐渐接近实际，估算质量是持续改进的。

### 3.3 全模态实现

全模态能力围绕 MiniCPM-o 4.5 组织，覆盖文本、语音、图片、视频和语音合成五种模态，统一走 Realtime WebSocket 协议。这一节说明每种模态的实现方式，以及两个后端的行为差异如何处理。

#### 3.3.1 双后端与切换机制

系统支持两个推理后端，通过环境变量切换：配置 `ASCEND_OMNI_WS_URL` 连接昇腾 A3 上的本地推理服务，配置 `MAP_REALTIME_API_KEY` 连接 ModelBest 云端 API，`/api/realtime/status` 返回当前后端类型，页面顶部同步显示当前模型与后端。两个后端在鉴权方式、事件时序和音频行为上存在差异，差异被收敛在实时客户端与音频适配层两个模块内，业务代码不感知后端；连接本地后端时关闭默认心跳，避免推理较慢时连接被超时断开。

#### 3.3.2 音频理解统一入口

音频理解集中在统一适配层，目标是让本地与云端的行为保持一致。本地路径直接向模型发送音频并获取回答，云端路径先转写再以文字理解，两者的上层结果相同；语音对话、答辩回合、会议旁听和语音汇报四个入口都经过这一适配层。

长音频的处理是音频链路的关键。系统按 12 秒分片，静音检测以 20 毫秒窗口计算能量，找到停顿点后按句切分，避免在说话中途硬切；分片最多三层合并，对本地后端的音频长度设有 10 分钟硬上限，防止长音频触发推理服务异常。转写结果经过质量校验，乱码片段、模型的客套应答和自我说明会被过滤或重试，保证展示的是用户原话。语音对话的跨轮记忆同样在这里实现：本地采用先转写、再纯文本回答、最后抽取用户信息的三段式流程，抽取到的信息与既有记忆冲突时以旧记忆为准，防止模型幻觉污染记忆；云端与文字共用完整历史；答辩模拟的文字、语音、视频输入共用同一份历史。

应用层为适配 8B 模型的输出波动设置了一组守卫。其中硬性限制（长音频分片、时长上限、语音合成降级）默认只作用于本地昇腾后端，云端链路不受影响；乱码与复读过滤对两端都生效，云端命中时自动带防重复指令重试一次，本地规则更严格。守卫只在模型输出异常或输入超过能力边界时介入，正常对话不会产生额外延迟。若自托管环境的本地后端性能完好，可以通过 `APP_LOCAL_AUDIO_CHUNK_SECONDS`（0 表示关闭分片）、`APP_LOCAL_AUDIO_MAX_SECONDS` 与 `APP_LOCAL_TTS_ENABLED` 三个环境变量放宽或关闭对应限制，无需修改代码。

#### 3.3.3 图片理解

图片理解覆盖拍照需求、白板照片、截图和手绘。模型在提取文字的同时描述图表、流程图和场景内容，理解结果作为需求材料参与任务拆解；扫描版 PDF 先渲染成页面图像再交给视觉模型。文件分析对每个文件给出明确状态：已读取、需要确认或无法识别；模型失败时保留文件元数据并提示人工确认，系统不伪造读取结果。

#### 3.3.4 视频理解

视频理解用于会议旁听和答辩表现观察。会议旁听对视频均匀采样抽取数帧，再提取音频轨道，画面与声音分别理解后合并输出会议要点、任务和风险；无声轨录屏仅凭画面内容也能完成整理。答辩视频回答由模型观察答辩者的神情、眼神和姿态，回复附带表现观察。抽帧采用流式处理，整段视频不一次性载入内存。

#### 3.3.5 语音合成

语音合成用于语音回复和今日播报。云端返回的音频为裸 PCM 格式，后端自动转换为浏览器可直接播放的 WAV。本地昇腾后端的语音合成存在上游算子问题，可能挂起推理服务，因此本地后端默认禁用语音回复（可通过 `APP_LOCAL_TTS_ENABLED` 开启）；语音合成失败时自动降级为纯文本回答，对话不中断。

### 3.4 合规与模型使用边界

本赛道要求应用围绕 MiniCPM-o 4.5 全模态能力开发，全链路只能使用该模型。本项目从三个层面保证合规。代码层，模型客户端工厂在合规模式下只创建 MiniCPM-o 客户端，不创建任何其他模型客户端；文本对话、图片理解、音频转写、语音合成、答辩问答等全部入口统一走该客户端。配置层，`APP_MODEL_MODE=minicpm` 与 `APP_ALLOW_EXTERNAL_MODELS=0` 构成硬约束，配置一旦生效，外部视觉与语音模型不可用。测试层，自动化测试以模拟实现替代真实模型调用，并保留对合规模式的专项断言，验证合规模式下不存在其他模型客户端。API Key 只存放于本地环境变量文件，不进入版本库。

### 3.5 数据、安全与存储

方案数据以 JSON 文件存储在本地 memory 目录，支持与 S3 对象存储同步；多用户场景支持账号、会话和方案级权限控制，密码以加盐哈希存储，操作审计记录方案变更。

版本管理是方案长期可维护的关键。每次保存生成一个版本节点，记录父版本、操作摘要和内容指纹；版本按保存顺序连成树，内容相近的版本按相似度归入可比版本族，方便比较"同一件事的不同版本"。对比可列出任意两个版本在任务、成员和设置上的差异；回滚从目标版本创建新分支，当前版本保留。每个版本保存完整快照，对比和回滚可直接基于任意版本完成，无需逐级重放；内容指纹同时用于并发覆盖检测，两人同时保存时能识别覆盖风险。

安全方面，分享链接只读且限时有效；远程文件下载经过 SSRF 校验，只允许预设主机；上传文件限制类型与大小；前端渲染用户数据统一转义；导出文件名经过清洗，避免路径注入。

### 4.2 登录与访问

公网实例开启管理端登录，账号与密码见摘要及 8.1；登录保护方案列表、删除和模型调用等管理接口。成员汇报链接保持免登录，负责人生成链接后发给成员即可使用。本地部署未设置令牌时，工作台直接可用。

### 4.3 快速开始

打开工作台后点击载入演示案例，系统会填入一个示例项目。正常流程为：填写项目信息与成员，选择 AI 生成或快速生成任务拆解，在草案中调整任务，确认拆解后进入分工页面，检查并调整负责人或协作者，确认后进入最终方案。确认阶段只等待拆解时的一次模型调用，快速生成不等待模型。

### 4.4 小型项目流程

小型项目适合成员已经确定、组织关系简单的场景。添加成员并填写姓名、身份、技能与每日可用工时后生成任务拆解；在任务卡片中修改名称、描述、工时、依赖和建议人数，支持新增、删除和合并；确认拆解后进入分工页面，检查负责人、协作者和工作量，确认后进入最终方案。

### 4.5 大型项目流程

大型项目适合活动、赛事和复杂项目，流程分四步：大模块拆解、骨干认领、子任务拆解、分工招募。系统先把项目拆成若干大模块，骨干为各模块认领负责人，再进入模块内部拆解子任务并设置依赖，需要额外人员的任务进入志愿者招募与认领流程。

### 4.6 最终方案功能

最终方案页聚合了任务计划、排期资源、团队负载、分工协作、执行复盘、项目报告、答辩模拟和提醒通知。任务计划展示状态、负责人、工时与执行情况，任务完成后可记录实际工时；排期资源展示时间线、关键路径、资源日历和冲突；团队负载展示成员工作量占比；分工协作支持成员增删与属性修改，应用变更后自动重算。

### 4.7 成员汇报页

保存方案后，负责人可以为任意成员生成专属汇报链接。成员在手机上打开链接即可看到自己的任务，用语音说出状态、工时和备注，或者拍摄交付物照片，识别结果经确认后应用。汇报采用负责人确认制，核心是一条完成不变量：任务标记完成，当且仅当全部成员的部分均完成且负责人确认。

具体运行方式是：每位成员维护独立的"我的状态"（我的部分完成、进行中、阻塞），任务级状态由成员状态聚合而来。成员上报完成时，任务进入待确认状态；负责人确认后才转为完成；任一成员改回未完成或报告阻塞，任务自动回退为进行中并通知负责人。这样设计的直接好处是，任务级状态始终是成员状态的函数，任何一端更新，另一端自动一致，从结构上排除了"任务已完成但某成员的部分没有完成"的矛盾组合；负责人确认制让"完成"同时获得执行方和把关方的确认，回退传播让异常一出现就可见。

工时与交付物同样有明确的规则：任务实际总工时取各成员最近一次带工时上报之和，纯状态变更且未报工时会使该成员退出工时累计；完成日期只有负责人可以设置和修改，协作者提交的日期不影响任务；负责人可以为已线下完成的志愿者补录确认，记录保留可追溯；交付物照片按权限查看。语音汇报识别出的状态、工时和备注先展示给成员确认，确认后才写入方案。大型项目中，骨干可以查看模块内成员进度，项目负责人可以查看团队总览。

### 4.8 导出、分享与版本管理

最终方案支持导出 Markdown、Word、PDF、Excel、CSV 和 ICS 六种格式；分享功能生成只读链接；历史方案通过版本树管理，支持差异对比与分支回滚。

### 4.9 常见问题

模型生成较慢时可以使用快速生成；答辩模拟只在项目要求包含答辩、汇报或路演时出现；团队负载无数据时先确认方案中存在已分配成员；排期避开的日期来自成员不可用日期、每日工时、任务依赖与截止日期的综合计算；AI 建议只提供分析，不会自动修改方案数据，实际修改仍需在编辑页面完成。

## 六、技术难点与解决

几个难点有一个共同点：模型输出天然带有不确定性，而业务系统要求结果稳定、正确、一致，系统要做的，是在两者之间建立一层可靠的转换。

### 6.1 模型输出与业务数据之间的对接

语言模型在自由对话中表现良好，一旦作为业务组件使用，就会暴露出格式错误、幻觉和重复内容等问题。例如拆解任务时模型可能编造不存在的成员，转写语音时可能把模型的自我介绍当成用户原话。如果让这些输出直接进入业务数据，方案的正确性就无法保证。

因此系统把模型当作一个可能出错的组件来处理，在它与业务数据之间设置多层校验与修正：结构校验剔除不存在的人物与任务引用，质量校验过滤乱码和模型的客套应答，转写结果清洗后才进入业务字段。语音对话的跨轮记忆遵循同样的思路：先转写、再以纯文本回答、最后抽取用户信息存入记忆。设计原则可以概括为一句话：任何校验失败的内容都不会写入业务数据，业务数据始终由确定性逻辑维护。

### 6.2 计划数据在动态变化中的正确性

方案生成之后，用户会持续修改任务、调整成员、切换状态，每一次变化都要重新计算排期与分工。如果这些计算依赖模型，结果会随模型输出波动，用户无法判断哪一次结果可信。所以计划数据的正确性责任全部由确定性算法承担：排期、技能评分、负载均衡和依赖校验都是纯算法，输入相同则输出相同；模型只负责任务拆解和审查建议这类创造性内容。任务完成状态由不变量约束，具体规则见 4.7；编辑操作在进入排期前经过结构校验，依赖环和悬空引用在源头被拦截。

### 6.3 多人协作下的一致性

主页面和成员汇报页可能同时操作同一份方案，两个入口都修改任务状态时，容易出现互相覆盖。系统用内容指纹检测并发修改，汇报页的状态更新统一走同一个重算入口，主页面在焦点回到页面时自动刷新，存在未保存修改时先确认再覆盖，避免双端各自写入。汇报令牌绑定方案与成员并设置有效期，交付物照片按权限访问，这些措施让"谁能看、谁能改"始终清晰。通知服务按平台适配企业微信、飞书和钉钉的消息格式，状态变更事件统一推送。

### 6.4 受限算力与多种终端下的可用性

昇腾推理服务存在会话级限制，长音频输入可能触发异常，移动端录音和摄像头又受安全上下文限制。会话限制通过演示前的预检和预热规避，长音频通过分片与时长上限控制（机制见 3.3.2），双后端切换保证任何一条链路出问题时演示可以继续。移动端方面，系统自动生成 HTTPS 证书监听备用端口，非安全环境下给出明确提示并回退文件选择，窄屏下完成全视图适配；多格式导出统一处理中文文件名与编码问题。这些限制针对本地推理服务设计。

### 6.5 工程落地效果

上述工程手段的最终效果是：在单卡昇腾环境和 16 GB 精度模型条件下，文本、语音、图片、视频四条链路在昇腾本地跑通，语音合成经云端后端补全，全模态能力整体服务于业务系统。这些效果可以现场核验：昇腾 A3 实测数据与公网云端链路都真实可访问，测试与演示不依赖任何不可复现的条件。

## 七、创新点

本章列出本项目区别于现有方案的两个核心差异，每一点都对应一组可以现场核验的行为。

### 7.1 全模态能力进入业务闭环

现有多模态应用大多把模型当作问答入口：用户发一张图或一段语音，模型返回一段回答，回答与业务流程没有关系。本项目的不同之处在于，四种模态分别接在业务链路的四个环节上——拍照进入需求理解，语音进入排期对话，会议录像进入任务整理，语音和照片进入进度汇报。每个模态入口都有明确的业务落点，模型输出直接参与任务拆解、状态更新和表现评估，形成从需求到执行的完整链路。这一点可以现场核验：拍摄一张需求截图，任务草案基于照片内容生成；上传一段组会录像，会议要点与任务直接进入拆解。

### 7.2 确定性算法保证计划正确性

生成式规划工具的常见问题，是把全部规划逻辑交给模型，结果不可解释、也不可复现。本项目让模型做它擅长的事，把正确性交给算法：CPM 关键路径、技能同义匹配、负载均衡阈值、不可用日期硬约束和依赖校验都有明确的算法语义。可以核验的行为是：在固定拆解与分工输入下，排期与负载均衡结果完全一致；修改一个工时后，排期与负载的变化可以逐项解释。

## 八、复现与部署

本章给出评委复现项目、查看效果所需的全部步骤，按入口分为公网体验、本地启动和昇腾部署三档。

### 8.1 公网体验

评委可直接访问 [collaboration-planner-demo-l6ag.onrender.com](https://collaboration-planner-demo-l6ag.onrender.com) 体验完整功能，登录账号为 admin，密码为 ascend2026。体验路径建议按第五章 5.5 的五步演示流程操作。实例闲置会休眠，首次访问加载较慢属于正常现象，访问后即完成预热。

### 8.2 本地启动

本地启动需要 Python 3.11 及以上环境：

```bash
pip install -r requirements.txt
cp .env.example .env
python -m app.main
```

Windows PowerShell 下将复制配置一行替换为 `Copy-Item .env.example .env`，其余命令相同。

应用默认监听 8000 端口。推理后端二选一：配置 `MAP_REALTIME_API_KEY` 走云端 API；配置 `ASCEND_OMNI_WS_URL` 指向昇腾本地服务，本地电脑需先把昇腾 28099 端口转发到本机。合规模式固定为 `APP_MODEL_MODE=minicpm` 与 `APP_ALLOW_EXTERNAL_MODELS=0`。`/api/realtime/status` 返回当前后端，可确认链路。

### 8.3 昇腾 A3 部署

| 项 | 取值 |
| --- | --- |
| NPU | Ascend 910C（A3） |
| 系统 | Ubuntu 22.04 容器（宿主机 openEuler 2203 SP4，aarch64） |
| CANN | 9.1.0-beta.1 |
| 推理框架 | llama.cpp-omni（CANN 后端编译，关闭 OpenSSL） |
| 模型权重 | MiniCPM-o-4_5-F16.gguf（约 16 GB） |
| 推理服务 | llama-omni-server，监听 28099，WebSocket 路径 /backend |

模型权重从 ModelScope 下载，目录包含主模型、音频编码器、视觉编码器、语音合成模型与声码器，是全模态模型完整落地的直接证据；编译与启动的完整步骤见复现文档，服务健康检查返回 `{"engine":"comni","status":"ok"}`。

### 8.4 验证命令

```bash
python -m app.main                  # 启动应用
python scripts/preflight_demo.py    # 演示前预检与预热
python -m pytest tests/ -q          # 全量自动化测试（401 项通过）
node --check app/web/static/app.js
node --check app/web/static/participants.js
```

### 8.5 故障排查

本地后端偶发识别不稳定时，注释 `ASCEND_OMNI_WS_URL` 即可切换云端，两者接口一致。推理服务挂起时在昇腾环境重启 llama-omni-server 并等待健康检查通过。摄像头不可用时回退为文件选择；视频处理耗时较长属于正常现象。系统提供故障演练脚本，可在评审前自动验证服务重启后的数据恢复。

### 8.6 部署到自有实例

仓库根目录提供 render.yaml 模板。部署到自有实例时设置 `MAP_REALTIME_API_KEY`，建议设置 `APP_ADMIN_TOKEN` 保护管理端，可选设置 `STORAGE_BACKEND=s3` 实现重启不丢数据。

## 九、已知边界与展望

### 9.1 已识别边界

模型能力方面，MiniCPM-o 4.5 为 8B 参数模型，数学与强推理能力有限，项目定位在感知与流程闭环，演示不涉及高难度推理。语音识别在本地昇腾后端存在偶发不稳定，处理方式见 8.5。语音合成默认只走云端后端，本地后端禁用相关开关，可通过环境变量开启。视频理解采用抽帧方式，单次处理帧数有限，长视频处理耗时较长，适合会议录像与答辩片段。

交互形态方面，当前为逐轮交互，尚未支持全双工实时对话；推理服务同一时间只支持一个活跃会话，演示前通过预检脚本预热并避免并发占用。答辩场景通过视频问答入口完成，回复附带对答辩者表现状态的观察。

### 9.2 展望

后续演进沿四个方向展开：接入全双工实时对话与视频实时帧理解；支持企业微信应用消息定向推送与组织通讯录同步；跟进上游视觉与语音合成能力修复，评估多卡负载均衡与更大上下文窗口；完善知识库跨组织复用、自动复盘与预测性风险提示。
